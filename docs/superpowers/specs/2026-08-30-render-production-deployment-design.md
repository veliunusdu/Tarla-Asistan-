# Render Production Deployment Design

## Goal

Deploy Tarla Asistani as a production web application on Render while keeping
Supabase PostgreSQL as the system of record, Firebase for identity and push
notifications, Cloudflare R2 for media, and DeepSeek for AI chat.

## Scope

This release deploys the ASP.NET Core API and Next.js web panel from the
repository's `main` branch. The Flutter application remains a separately built
mobile client and receives the production API URL through its existing
`API_BASE_URL` build configuration.

## Architecture

Render hosts two public Docker web services in the same region:

1. `tarla-asistani-api` builds from `backend/Dockerfile`, listens on Render's
   assigned port, and exposes `/health/ready` as its health check.
2. `tarla-asistani-web` builds from `web/Dockerfile` and receives the public
   API URL through `NEXT_PUBLIC_API_URL` at build time.

The API uses the existing Supabase PostgreSQL connection string. No Render
PostgreSQL instance or local Docker database is created. API persistence is
therefore independent of Render instance restarts and deploys.

## Configuration And Secrets

`render.yaml` declares both services, Docker paths, health checks, and the
names of all required environment variables. It contains no secret values.

The API service receives these secrets only through Render's environment and
secret-file features:

- `DATABASE_URL`
- `JWT_SECRET`, generated by Render
- `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`
- `DEEPSEEK_API_KEY`
- `FIREBASE_PROJECT_ID`
- Firebase Admin service-account JSON as `/etc/secrets/firebase-service-account.json`

The API configuration uses the secret-file path above. Production sets
`ASPNETCORE_ENVIRONMENT=Production`, `FIREBASE_AUTH_ENABLED=true`,
`AI_CHAT_PROVIDER=deepseek`, and `MEDIA_STORAGE_PROVIDER=r2`. Push delivery is
wired directly to Firebase Admin in the backend, so it is enabled only when the
Firebase service-account file initializes successfully.

The web service gets only the non-secret public API URL at build time. Its URL
is registered as `WEB_ORIGIN` for API CORS. A custom domain can replace the
initial `onrender.com` URL without architectural changes.

## Authentication And Notifications

Firebase Authentication Phone provider is enabled in project `demo2-c4265`.
The Render web hostname and later custom domain are added to Firebase
Authentication's authorized domains. A physical Android release build uses the
same Firebase project, is built with `API_BASE_URL` pointing at the deployed
API, registers its FCM token after sign-in, and receives one test notification.

## Database And Migrations

Supabase already has the EF Core migration history and application schema. The
API runs migrations idempotently on production startup. Before first deploy,
the `postgis` extension is verified in Supabase. The Supabase Data API is not
used by this application; public API-role access is reviewed and restricted or
RLS policies are applied before public launch.

## Credential Rotation

Credentials previously exposed outside a secret manager are rotated before
production deployment: Supabase database password, R2 access key pair,
DeepSeek API key, and Firebase Admin service account. New values are entered
only in Render and local ignored environment files; none are committed.

## Deployment Sequence

1. Commit the Render Blueprint and production-safe configuration changes to
   `main`, excluding unrelated generated mobile files and all secrets.
2. Connect the GitHub repository to Render and create services from the
   Blueprint.
3. Enter the rotated secrets and upload the Firebase secret file in Render.
4. Deploy the API, verify `/health/ready`, and review migration logs.
5. Deploy the web panel using the actual API URL and verify browser login.
6. Add the web domain in Firebase, test Firebase phone sign-in, R2 upload,
   DeepSeek chat, and FCM delivery from a physical device.
7. Add the custom domain and repeat health, authentication, CORS, media, AI,
   and notification checks over HTTPS.

## Acceptance Criteria

- Both Render services are healthy and automatically deploy from `main`.
- The deployed API reads and writes Supabase data without schema errors.
- The web panel can authenticate against Firebase and use protected API routes.
- An uploaded case image is stored in R2 and can be read back by an authorized user.
- DeepSeek chat returns a response through the deployed API.
- A physical Android device receives an FCM notification after registering a token.
- No secret appears in Git history, Render Blueprint files, or browser-visible configuration.
